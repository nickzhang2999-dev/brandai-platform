范围：用户新增反馈中的“上传已失败，但附件一直处理中、删除按钮灰色、继续项目仍被交接弹层挡住”。本报告补充先前交接收尾报告，不覆盖其历史成功回执。

## 1. 修前复现

用真实 Chrome headless、真实首页交接脚本和 IndexedDB，在 loopback HTTP 夹具中返回合法的 `FAILED` 上传任务。原有 7 项首页浏览器检查仍通过；新增终态失败用例在首个断言失败：`queued !== error`。

修前观察：

| --- | --- |
| 服务端夹具状态 | `FAILED` |
| 附件卡片状态 | `queued` |

| 移除按钮 | disabled |

| 原始 File | 仍保存在 IndexedDB，非空 |

证据：`.novart-build/upload-recovery-baseline-browser-report.json`、`.novart-build/upload-recovery-baseline-failure.png`。基线源文件单独保存在 `.novart-build/temporary/upload-recovery-baseline-home-start.js`，所以修后测试未覆盖修前结果。

这个复现确认的是前端终态处理缺口，不证明用户原文件的格式问题。真实上传记录的调查另见[上传失败调查](./home-upload-failure-investigation-2026-10-19.md)。

## 2. 修后行为

- 核实为 `FAILED` 的附件显示失败状态，可以移除。删除最后一张失败附件结束原交接，保留已创建项目及文字需求，不自动变成无参考图生成。
- 可以明确结束交接并进入项目；保留原始 File 为未提交草稿，已有项目和服务端素材不被删除。
- 已知损坏或不支持格式提供“更换失败图片”；普通处理失败允许明确重传。重传使用新的上传幂等身份，已有项目及首次创作身份保持不变。
- 上传、首图创作结果未知时继续冻结删除和结束操作，只能核对原请求；刷新时先 GET 核实已知任务，未核实前不能放行删除。
- 删除、结束和重传的 IndexedDB 写入失败会回滚内存状态；不会提前清掉原始文件或显示成功。
- 多标签页对同一项目使用 Web Lock。操作前重读恢复记录并同步已开始/已接受的创作标记；另一页已结束交接时，保留它留下的文件草稿。
- 未知服务端错误只显示安全的固定说明，不原样输出内部地址或参数。

完整 Studio 壳用例直接加载实际 `studio.html`、bootstrap、路由和首页脚本，真实点击以下流程：

**文字 + 图片 → 失败 → 结束交接 → 原项目解锁 → 打开另一个已有项目 → 刷新 → 返回首页，需求与文件仍在 → 移除草稿附件 → 新建并进入空白项目 → 新文字开始创作一次。**

该流程确认创建了 3 个不同的测试项目、只接受 1 次新的首次创作，最初失败项目一直保留；刷新后也没有重放旧失败交接或再次生成。这补足了首页模块夹具的空白按钮只检查“不生成”的覆盖边界。

## 4. 独立代码复核

只读检查当前上传恢复 diff 后，未发现本轮仍未解决的阻断项：

- `uploadStarted`、`creationStarted` 在发请求前持久化，未知响应不会被误判成尚未提交。
- `replaceRecovery` 持久化失败恢复原列表和提交对象；原 Blob 的 URL 只在成功移除或成功替换后释放。
- 结束交接不请求删除项目/素材，不提交生成；新草稿身份只留在本地，直到用户再次明确提交。
- 已核实的任务结果继续通过项目、任务、mutationId、素材归属校验，未放宽后端图片验证。
- 多附件删除弹层依据 `removeItem` 返回的实际成功结果更新；已补测试验证落盘失败时不显示“已移除”。

该复核及测试不代表所有跨浏览器竞态已穷尽；本轮为 Windows Chrome，未在 macOS Safari 或不支持 Web Locks 的浏览器中进行真机测试。

## 5. 服务边界

测试的文件输入、DOM、IndexedDB、路由与页面脚本是真实执行；项目、上传任务和编辑器回执由明确标注的内存 HTTP 夹具提供。没有真实模型调用、共享数据库写入、CDS 部署，也未把夹具图片当模型产出。

用户原文件仍可能被后端格式/像素/解码校验拒绝。前端恢复修复保证失败有出口，不等于原文件已经能够上传成功；不能把这两件事混成同一项验收。
