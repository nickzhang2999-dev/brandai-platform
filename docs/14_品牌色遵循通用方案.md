# 品牌色遵循通用方案

> 2026-11-04 审查边界：本文后续方法属于待验证方案，未运行付费生成对照实验。现有颜色检查只做整图 96px 抽样和近似色覆盖统计，不能定位主体、认定模型未遵守或代替人工质量验收。无回执也可能是历史任务或检查失败，不能直接判定未录入颜色。文中的效果、保证及优先级表述均不是已证实结论。
>
> 适用问题：品牌规范里写了颜色，生成结果仍是别的颜色（典型：品牌绿，出来红苹果）。
> 本文只谈**怎么让颜色更可能被遵循、以及当它不遵循时怎么保证交付**，不谈"让模型必须听话"——那做不到。

---

## 一、先定性：这不是一个 bug，是四类不同的失败

看到"颜色不对"就去调提示词，是最常见的错误起点。先分层归因，否则改错地方。

| 类别 | 表现 | 判据 | 责任方 |
|---|---|---|---|
| A. 规则没下发 | 提示词里根本没有颜色 | 回执 `appliedRuleCount = 0`，或 `reason = NO_APPLICABLE_RULES` | 产品/配置 |
| B. 没有颜色规则 | 品牌只存了字体/布局 | 回执无 `colourFidelity` 字段 | 品牌知识录入 |
| C. 规则下发了，模型没遵守 | 提示词里有，成品里没有 | `appliedRuleCount > 0` 且 `colourFidelity.missing` 非空 | **模型** |
| D. 需求本身冲突 | 用户要"红苹果"，品牌色是绿 | 提示词与品牌规则矛盾 | 需求侧 |

**只有 C 类需要下面这些方法。** A、B 类去修配置，D 类要问用户"以哪个为准"。

现有实现：`apps/web/src/lib/brand-colour-fidelity.ts`（`checkBrandColourFidelity`）在出图后跑一次，把结果写进版本 `params.colourFidelity`，回执据此显示。它只负责**区分 A/B/C**，不负责让模型听话。

---

## 二、五层解法，按"保证程度"递增

下面每一层都比上一层更贵，但也更接近"保证"。**不要一上来就上最贵的。**

### L1 · 提示词结构优化（待对照验证，不保证）

影像模型对提示词的**位置和具体度**敏感，对抽象调色板名单不敏感。

**反例**（当前实现就是这么写的）：

```
brand palette: #34A853, #F4F0FF
```

模型读到的是"有这么几个颜色"，不知道往哪用。

**正例**：

```
画面主体的苹果表皮为纯绿色 #34A853，同一色相不得偏红。
【禁止】红色、深红、枣红、橙色苹果表皮。
```

四条规则：

1. **前置**：颜色指令放在提示词最靠前，模型对开头权重更高。
2. **落到物体上**：不说"品牌色是 X"，说"<具体物体> 的 <具体部位> 是 X"。
3. **显式排他**：把竞争色写进 negative prompt。扩散模型对"不要什么"的响应比"要什么"更直接。
4. **首尾各一次**：关键色在开头和结尾各出现一次，中间被稀释时仍有残留。

对应到代码：`apps/web/src/lib/ai-constraints.ts` 里 `promptAdditions` 目前只 push 调色板名单和规则 summary。若要做 L1，应改为按物体生成句子，而这条信息来自用户需求（"苹果"），需要把需求和规则拼在一起再下发。

> 风险：描述越具体，越可能与用户原意冲突。必须与 D 类检查（需求 vs 规则一致性）配套。

---

### L2 · 参考图锚定（效果显著，成本中）

图像条件 > 文本条件。这是**性价比最高的一次跃升**。

两种用法：

| 方式 | 做法 | 适用 |
|---|---|---|
| 色卡锚定 | 上传一张只含品牌色的色块图作为 reference | 通用，最稳 |
| 素材锚定 | 用品牌已有实拍/主视觉作为 reference | 有现成素材时效果最好 |

实现落点：`studioReferences` / `aiConstraints.referenceImages` 已经把参考图送到 AI 服务，只是当前不用于强制颜色。增补一条"品牌色卡"作为固定 reference 即可，不需要改链路。

> 注意：参考图会同时带来构图/风格影响，不只带颜色。若只想影响颜色，色卡比实拍安全。

---

### L3 · 多候选 + 自动择优（工程保证，成本 N 倍生成费）

多候选只增加选择空间；自动择优本身不能构成对外质量保证，须结合可靠评估与人工验收。

```
生成 N=4 张
  → 每张跑 checkBrandColourFidelity
  → 排序：withinBrand 优先，其次 present 数量，再次 present 总占比
  → 交付最优的一张；其余仍保留为候选
```

优点：

- 不依赖提示词玄学，用现成的核对函数直接打分
- 失败率从"单张约 30–50%"降到"4 张全失败"，按独立事件估算 < 5%
- 结果可解释：回执能说"4 张里 3 张含品牌色，交付了覆盖最高的一张"

代价：生成费用 ×N，耗时 ×N（可并发，耗时基本不变）。

实现所需：现有 `/v1/generate` 已支持多版本返回；核对函数已具备。缺的是"择优后标注"这一步。

> 这是本文推荐作为**默认方案**的一层。

---

### L4 · 后处理色彩校正（强制保证，需蒙版）

对成品做色彩映射，把目标区域拉到品牌色。**这是唯一真正"保证"颜色出现的方法**，代价是可能失真。

两种粒度：

| 粒度 | 做法 | 风险 |
|---|---|---|
| 全局色调映射 | Lab 空间把整图色相往 palette 拉 | 全图偏色，通常不可接受 |
| 局部替换 | 需要蒙版选中目标物体，只改该区域 | 需要分割能力，边缘易脏 |

**不建议默认开启。** 只在"品牌色必须精确出现"的场景（如必须出现 logo 紫）作为显式选项，且必须让用户看到"这是校色后的结果"。

---

### L5 · 换生成链路（最彻底，成本最高）

| 方案 | 颜色控制力 | 代价 |
|---|---|---|
| ControlNet（颜色/线稿条件） | 强 | 需自建推理，非 OpenAI 兼容 |
| IP-Adapter | 强（图像特征注入） | 同上 |
| 品牌色 LoRA 微调 | 最强 | 训练成本 + 维护 |

只有在 L1–L3 仍不能满足业务要求时才考虑。**换链路等于换架构，不是调参。**

## 三、决策表

| 场景 | 推荐组合 | 预期 |
|---|---|---|
| 内部参考稿，颜色大致对即可 | L1 | 10–30% 改善 |
| 对外交付，必须"看得出来是品牌色" | **L1 + L2 + L3** | 单次交付合格率 > 95% |
| 品牌色是硬性合规要求 | L1 + L2 + L3 + L4（局部，显式） | 接近 100%，但需人工确认观感 |
| 高频、量大、颜色是核心卖点 | L1–L5 | 取决于链路建设 |

---

## 四、验收标准（不要用"看起来像"）

用可量化的判据，否则每次都要吵。

| 指标 | 阈值 | 说明 |
|---|---|---|
| 品牌色存在 | ΔE(CIE76) ≤ 22 且覆盖 ≥ 0.5% | 当前 `checkBrandColourFidelity` 默认值 |
| 多候选合格率 | ≥ 75%（4 张里至少 3 张含品牌色） | 低于此说明 L1/L2 没生效 |
| 主色占比 | 目标物体区域 ≥ 40% 为目标色 | 需蒙版，属 L4 验收 |

> 中性色（近白/近黑）不参与判定。任何白底图都能"命中"浅色品牌色，把它算通过是自欺。

---

## 五、明确不做的

1. **不声称"规则已应用"就等于"颜色正确"**。规则进提示词 ≠ 模型遵循。措辞必须区分"传入"和"生效"。
2. **不对历史结果补推断**。没有核对记录的旧任务显示 `null`，不能默认"通过"。
3. **不做全局自动校色**。全图偏色比颜色不对更伤品牌。
4. **不用单一 ΔE 判定"合格"**。颜色对但构图崩了，仍然不可交付；核对只是必要条件。
