# NovartLab 发布失败回溯报告

日期：2026-10-20。本文时间统一为北京时间（UTC+8）。
适用对象：客户维护负责人、早期部署交付方、CDS 平台维护方。

## 可直接向客户说明的结论

本次失败由新版本与既有生产发布校验不兼容触发。客户维护期间的自有
Studio 资源重构有意停止生成旧的 `novart-product-worker.js`；生产服务器
独立维护的发布脚本仍要求这个文件必须存在，因而拒绝了新版本。旧版本
包含该文件，所以此前能正常发布。CDS 的发布前检查只确认命令配置、
连接、目录和脚本可执行等条件，没有执行这项项目资源校验，因此出现
“预检通过、正式发布失败”。

这是可以定位到具体代码变更和旧校验规则的发布兼容性遗漏。现有证据
不支持“服务器突然坏了”或“新人随意删错文件”的结论。客户侧代码改变
了发布产物，交付时的服务器独立脚本又未与项目一起演进，平台预检未能
提前揭示这个差异，三者共同形成了本次问题。客户负责维护代码的新人
身份由客户确认；Git 署名本身不能证明实际操作人员、审批人或知情范围。

## 为什么之前一直成功，最近才失败

旧导出器会生成 `novart-product-worker.js`，用于旧画布资源访问。旧脚本
把这个文件与 `studio.html`、bootstrap 一起视为永久必需资源。旧版本
同时满足两套规则，因此此前成功并不矛盾。

`e0725bd` 对此做了完整、有意的改变：导出器删除 worker 生成代码；前端
停止注册它，并清理同源旧注册；新增导出测试明确要求 manifest **不包含**
这个 worker。新镜像没有它符合新版本的设计和测试。

生产脚本位于项目仓库之外，依然坚持旧要求。包含这个改动的版本首次走
这条旧发布路径时，校验必然失败。重复点击、重新构建同一份代码，或让
另一个 Agent 只调用发布接口，都不会改变这个确定性结果。

为验证因果，已将修复前的原始资源校验分别用于两份真实镜像的资源副本，
验证在临时目录中进行，不执行发布、不触碰线上 current。旧镜像 `2d29125`
通过 124 项资源校验，新镜像 `19f19af` 稳定报出相同断言。结果另存于服务器
受限目录的 `original-validator-reproduction.json`。

## 对客户维护代码的判断

直接触发点确实来自维护期间的代码变更，不能说与客户侧改动完全无关。
但退役旧 worker 与自有资源/自研画布迁移方向一致，有对应的调用方调整、
旧注册清理和测试。没有证据表明该文件是误删，亦不能仅凭发布失败认定
新人违反了项目设计。

可确认的工程遗漏是：**发布产物发生变化，没有连同实际生产发布路径做
兼容性检查和更新。** 这属于变更交付完整性问题。至于维护者是否已收到
该服务器脚本、是否被告知其隐藏要求、是否经过负责人审批，需要结合
交接材料判断，本报告不以 Git 署名替代这些事实。

## 早期部署方案与 CDS 的责任边界

早期采用现有脚本模式能够发布当时版本，历史记录也证明其曾多次成功。
其长期缺点是发布逻辑留在服务器外部文件里，不能自动随项目 Git 版本
升级或回滚；脚本中的具体资源清单容易变成隐藏约束。正常业务重构后，
这种方式需要人工同步，维护者仅看到项目仓库就难以发现全部发布要求。

CDS 确实提供动态 Compose 和动态静态站发布，但该目标实际配置的是
`existing-script`，命令为 `/opt/brandai-platform-prod/local-prod-release.sh`。
它没有使用动态模式。CDS 不能仅凭旧配置自动推断安全的生产数据卷、
私密配置和入口映射，因此一次升级也不会自动完成站点迁移。

CDS 另有明确的可改进项：existing-script 的 `scriptSha256` 是命令字符串
的哈希。本次记录的 `93e9bcfa...` 恰好等于上述路径字符串的 SHA-256，
不能证明被引用脚本正文未变化。页面“核对执行脚本哈希”的表达容易造成
过度理解；发布预检也没有覆盖项目内部资源校验。已核对的远端 main
`38a158d64a558aed305dbe57066e014004b62d50` 仍存在这些行为。

因此，**CDS 需要改进现有脚本模式的内容指纹、预检覆盖说明与迁移引导**；
但修复本项目不必等待整个平台升级，可以使用已有动态 Compose 能力，
把生产配置和检查纳入项目版本。本次迁移不宣称已修复 CDS 所有目标的
existing-script 通用问题。

## 修复方式是否长期有效

把服务器脚本改为依据 manifest 校验，是针对当前错误的有效修复，并非
过几天自动失效的临时补丁。它也消除了同类“资源正常退役仍被硬编码要求”
的问题。不过，脚本仍独立于项目版本，未来仍有其他同步遗漏的可能，
所以仅保留这个修补不足以形成长期交付方案。

最终方案按客户确认，采用**项目提供脚本、CI 审查、CDS 执行**，而不是由
CDS 猜测项目应该怎样部署：默认文件 `cds-release.sh` 和代码一起提交，
PR CI 与镜像流水线执行同一文件的 `check`；CDS 只执行完整提交对应的
`check / deploy`，记录正文指纹，不读取生产机上可漂移的旧脚本。独立
保存在 CDS 的脚本只作为明确选择的备选，缺少项目文件时不得自动兜底。

本项目脚本调用仓库内的生产 Compose、资源验证器与入口配置。同一提交
镜像负责 Web、AI 与 Worker，复用原有私密配置和数据卷；先完成迁移与
服务就绪，再检查真实入口及 manifest 中的资源。代码退役或新增资源时，
维护者必须同步调整脚本及测试，Agent 门禁禁止删检查、跳过 CI 或切回
旧模式绕过。后续正常发布、回滚使用 CDS 页面，无需登录服务器改脚本。

两个仓库经 PR 检查并合并，维护分支同步发布合同、历史分支不动。最终
上线结果以同一提交的真实控制台发布记录和公网验证为准；本报告中的
历史复现与隔离测试不冒充本轮正式发布回执。

## 影响范围与另外发现的问题

本次断言发生在同步 current 和替换容器之前，旧生产版本继续提供服务；
本次发布失败不等于站点整体中断，也没有该错误导致数据删除的证据。
Ubuntu Apport 随后报告 `/opt/brandai-platform-prod/-` 不存在，是处理
`python3 -` 异常时的二次错误，不是业务目录真的丢失。

迁移审计另外发现生产库有 11 项已在项目中的迁移尚未执行。它们**不是**
本次 `Required Studio resource missing` 的触发原因，但说明旧发布流程
没有完整覆盖数据库同步，仅看健康接口不足以证明全部功能可用。已完成
真实 PostgreSQL/Redis 备份、隔离恢复与 11 项迁移演练；26 类工作区归属
检查及 6 类跨资源关联检查均为 0 异常。正式执行结果单独记录。
