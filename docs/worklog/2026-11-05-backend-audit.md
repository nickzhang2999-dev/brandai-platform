## 问题明细

### P1-1 任务恢复与领取缺少部署环境归属

main和分层预览的数据库身份摘要相同。两边Redis队列前缀各自独立，但都扫描同一张数据库任务表，将同一批PENDING任务送入自己的队列。生成任务领取只核对任务状态、权限、内容摘要与期限，缺少执行环境限制。

影响涵盖生图、文案、对话、分层、生成后检查及自动PSD续接。最终由哪一版后台先领取会影响处理逻辑。隔离用例调用同一恢复函数，在两种部署身份下观察到同一个请求被重复投递。

线上新增输出中，有一张带新保真计划的图片，其最终版本只有品牌报告，保真报告和快照绑定都缺失。该记录与旧检查逻辑处理新任务相符。现有记录未保存实际执行者SHA，具体执行分支仍无法唯一追溯。

定位文件为 `apps/web/src/lib/studio-generation.ts` 第110行、`studio-generation-lifecycle.ts` 第28行、`workers/studio-writing.worker.ts` 第9行和 `studio-generation-compliance.ts` 第99行。两端线上源码与数据库身份摘要保存在 `isolation-evidence.json`，结果关联保存在 `report-bindings.json`。

建议先确定预览数据库隔离方案，或同步修改所有消费者的任务归属约束。仅给新分支追加过滤条件无法约束仍在全库扫描的旧消费者。应补受理环境、执行环境、执行SHA及模型快照，覆盖受理、恢复、领取、超时与归档全流程。

### P1-2 当前文案通道处于禁用状态

正常体验账号通过文案接口要求的当前用户校验后，已有项目的 `studio-writing` GET返回HTTP200、`enabled=false`。分层预览和main运行中的worker进程均缺少 `COPYWRITING_API_KEY`、`COPYWRITING_BASE_URL` 和 `COPYWRITING_MODEL`。

代码中的文案通道只读取这组独立环境配置，并使用Anthropic messages协议。后台通用生图、VLM与分层设置来自AppSetting，两条配置读取路径分开。已配置通用模型无法自动启用文案生成和风格提取。

定位文件为 `apps/web/src/lib/studio-copywriting-provider.ts` 第5行、`studio-writing-provider.ts` 第92行及 `studio-writing.ts` 第83、180行。证据为 `writing-http-state.json` 和 `writing-runtime-config.json`。

建议核对公司已有文本接口的协议与凭据来源，恢复Web与Worker一致的运行配置，增加管理员可见的通道状态。随后通过实际文案、选段改写和风格提取各做有界验收。当前数据库里文案类型任务的成功记录不能代替当前通道可用性检查。

### P1-3 灵感库第一页被后台当成完整知识库

近期分页改动令 `listCases()` 默认返回50条。检索、分析权限复核、问答引用复核和收藏读取仍调用默认列表，并将返回的cases作为全库。

已用隔离用例复现三个表现。

- 第51条仍有效且允许分析的案例，被权限复核过滤并提示引用已更新。
- 仅第51条匹配的关键词无法被灵感助手检索到。
- 已保存的第51条收藏被返回为 `unavailable=true`。

线上正常GET确认库内229条，第一页50条，第二页50条且与第一页无重合。179条位于默认第一页以外。页面带关键词的列表搜索与助手后台检索走法不同，故页面能找到案例仍可能无法在助手中使用。

定位文件为 `apps/web/src/lib/inspiration/service.ts` 第31行、`retrieval.ts` 第10行、`access.ts` 第29行、`worker.ts` 第24、48、52、60行，以及收藏GET中的默认 `listCases` 调用。

建议将分页展示与后台证据查询分开。检索使用有界的完整候选集，指定案例和历史引用按ID、版本及权限读取，收藏按已存引用读取。回归需覆盖第51/201条、跨页历史引用及撤回。该回归与 `f10d043` 中的分页修改有关。

### P2-1 缩略图对象缺失后的恢复缺口

数据库已有 `previewStorageKey` 时，原图代理直接读取该对象。对象缺失会进入通用500错误。预览worker看到已有字段也会直接返回，无法重建缺失对象。

隔离用例已证明缺失缩略图返回500，且未触发重建。线上Web日志另有4次 `NoSuchKey`，但当前日志只包含请求标识，无法把这些历史错误确定关联到缩略图。正常账号抽查的3组原图和缩略图当前均返回200。

定位文件为 `apps/web/src/app/api/workspaces/[wsId]/assets/[assetId]/raw/route.ts` 第77行，以及 `apps/web/src/lib/workers/image-preview.worker.ts` 第115行。

建议区分源文件缺失与缓存缺失。缓存缺失可在并发保护下清理失效引用并安排重建，源文件缺失应返回明确状态并提供恢复路径。补充资源ID与操作阶段的受控诊断信息。

### P2-2 保真汇总字段超限会使完整核验计划失效

每条品牌规则已单独进入约束清单，`compiled-context` 又把编译后的全部规则重复序列化到单个 `expected` 字段，该字段上限4000字符。只要这个汇总项超限，`safeParse` 就把整份plan置为null。

隔离用例使用12条约400字的有效品牌规则。单条规则清单可正常编译，加入编译汇总后整个计划失效。清单条数仍远低于64项。

线上另有一次真实核验的颜色、身份、轮廓、标志、文字和数量通过，区域与compiled-context为unknown。该记录属于检查粒度和证据能力问题，不能将其归因于上述长度溢出，因为其计划仍有效。

定位文件为 `apps/web/src/lib/studio-visual-fidelity.ts` 第84行和后续整份计划校验。

建议逐项编译适用视觉要求，将模型参数和执行说明单独保存。对局部无法核验项保留unknown，避免重复文本导致全部检查失效。实际照片的复合要求仍需模型质量验收。

### P2-3 镜像环境持续执行无效Git检查

当前worker每15秒执行一次 `git rev-parse HEAD`。部署镜像没有Git命令，读取的500行worker日志中持续出现 `spawn git ENOENT`。版本检查失效，同时重复日志挤占排障窗口。

定位文件为 `apps/web/src/lib/workers/index.ts` 第166、177行。

建议按部署模式选择版本检查方式。不可变镜像核对构建SHA，源码挂载环境保留Git漂移检查，并对检查能力缺失做一次性可见提示。

### P1-4 分层仅恢复文件尺寸，模型低分辨率像素仍被整体放大

只读查询现有成功任务，最新一条创建于北京时间2026-11-04 18:11:20。原图为736×980，4个图层的实际模型输出记录均为544×736，再以LANCZOS3放大为736×980。横向约1.353倍、纵向约1.332倍，模型返回像素数约为原图的55.5%。该比例描述像素数量，不能直接换算成视觉质量下降百分比。当前查询成功记录共5条，其他4条旧任务缺模型输出尺寸记录，不能推断其有效分辨率。

`studio-decomposition.ts` 第340–344、398行从受理原图对象读取并核对内容摘要和尺寸，再传原图数据给分层服务。`FalLayerProvider._body` 第2364行附近没有指定高分辨率输出参数。`studio-decomposition-images.ts` 第92行将小图插值放大，第126–128行记录缩放及 `rgbSource: PROVIDER`。归档流程没有在可见区域恢复原图RGB。PSD编码器读取这些已归档PNG，在校验尺寸后写入像素，没有再次缩小，但无法恢复上游已经丢失的纹理。

此前尺寸对齐、分辨率来源记录和提示已接入，不能据此认为清晰度修复完成。独立抠图工具有原图RGB结合模型alpha的保护能力，当前整体分层归档流程未复用该能力。直接把原图RGB铺到所有图层也不正确，会将前景带回背景，并破坏隐藏补全、半透明和阴影。

后续方案应先识别可见原像素、边界、遮挡补全和阴影归属。在对齐与区域归属可信的可见主体区域保留原图RGB，细化原尺寸蒙版。隐藏区域走单独补全，并明确属于生成内容。对文字、Logo、细线和草地等高频纹理做原尺寸局部对比，兼顾完整合成与单层独立使用验收。供应商高分辨率能力需要另行核实并实际测量，不能只添加未经确认的参数或用插值冒充高清。

证据保存于 `D:/coding/.novart-tmp/backend-audit-20261105/layer-resolution-evidence.json`，仅含时间、尺寸与缩放记录。本轮未触发付费分层，未逐像素检查该任务原文件，也未将这条记录认定为用户此次看到的具体任务。实际用户当前案例的局部模糊及画布额外缩放影响仍需对应原图/图层对照确认。
