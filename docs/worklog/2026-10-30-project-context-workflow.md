# 2026-10-30 项目资料复用与主稿工作流开发日志

## 本次解决的问题

用户确认继续借鉴 Lovart 报告中的资料复用、素材职责、主稿继承和分项审核流程。本次把已确认的项目资料连接到现有生图对话与文案任务，减少重复填写；同时保留当前修改对象、用户本轮要求和旧任务的原始行为。

实现位于 `claude/layer-quality`。报告中的 Skill 是设计依据；没有把它当成已取得 Lovart 服务端抠图或遮挡修复算法的证据。

## 前端使用变化

1. 现有“项目内容”侧栏增加一个默认可折叠的“项目资料”，保存目标、受众、确认文案和视觉要求。刷新从服务端恢复，版本冲突保留用户输入并要求明确选择。
2. 在已有素材列表区分产品事实、品牌标识、文案内容、视觉风格。这些职责不同于当前引用的 `REFERENCE / ADAPTIVE / EXACT` 用法，不增加素材权限。
3. 可把可信、已保存的画布图片设为“后续主稿”。沿用设计方向时仍以本轮明确要求为准，当前选中的图片继续作为修改对象；清除主稿不删除画布图片。
4. 对话显示“沿用项目资料”开关。文案显示实际沿用的资料版本。读取、保存、冲突或来源失效期间阻止带问题资料提交，不静默忽略用户已选择的资料。
5. 产品主图、广告海报、包装设计提供三个可选起点。只补空白目标与要求，保留已有文案、受众、主稿和素材。内容先进入未保存草稿，不调用模型、不自动确认、不另建工作台。

## 后端与数据变化

- `WorkbenchProjectState` 新增独立 `contextRevision / contextJson / contextUpdatedAt`；`StudioProjectContextMutation` 保存按工作区、项目、用户、mutation 隔离的回执；`StudioConversationMessage.projectContextJson` 保存受理时的快照。
- 新增项目域内 GET/PUT `studio-project-context`。服务端验证用户、项目写权限、素材归属、哈希、版本、画布原图与保存版本。失效来源保留记录并返回问题，用户可移除或重新选择。
- 请求只有显式带 `projectContextRevision` 时才冻结资料。后来的资料编辑不改变已受理任务；旧请求没有字段时沿用旧路径，未知回执按原 mutation 与快照恢复。
- 生图规划接收素材职责和主稿引用，图像提示词确定性携带已确认事实。当前显式目标和用途优先。合计超过 8 张引用或提示词预算时明确拒绝，不默默丢素材或截断确认文案。
- 文案只自动复用确认的文字事实。主稿、角色图片不会暗中变成文案的视觉输入；仍由“添加资料”明确选用。`COPY` 职责本身不执行 OCR。
- 执行前、模型调用前和最终归档复验来源与权限。图片版本记录保留服务端确认的主稿来源及素材职责，不接收 provider 伪造的来源字段。文案最终事务锁定项目和涉及的来源，准备附件期间撤销权限会阻止模型调用。
- 数据迁移为追加字段与表，不覆盖已有 brief、notes、workflow、画布或素材。

## Omni 接续入口

旧的 `OmniAssetWorkflow` 仍不是已接通的完整审核发布链路。现有分析任务没有可信的人工审核、用途授权或发布状态，历史终态任务也已清掉原请求，不能补造这些字段。

本次新增已鉴权只读入口：

`GET /api/internal/inspiration-analysis/jobs/{jobId}/workflow-evidence`

未来任务仅保留 request ID、素材 ID、原请求声明的版本和哈希摘要；终态继续清除图片字节与素材全文。回执明确 `source_basis=authenticated_request`，并不声称验证了 Omni 当前原图版本。历史缺失为 null；人工审核、AI 审核、用途授权、发布状态未知，`workflow=null`、发布资格为 false。原来的 strict job 响应保持兼容，未改变额度、定时任务或自动发布逻辑。

具体后续字段要求见 [Omni 接续约定](../omni-analysis-review-extension.md)。

## 独立审查与修正

- 补齐新 Omni 证据路由的精确 middleware 放行，使其可进入原有 Bearer 鉴权；相邻内部路径仍拦截。
- 文案准备文件之后、模型调用之前再次验证成员写权限，补撤销期间不调用模型的负例。

- 资料正在读取或保存时，文案与对话都阻止静默降级为“不沿用”。
