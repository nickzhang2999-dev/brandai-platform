# 首页竖版图片上传失败：只读调查

日期：2026-10-19
取证环境：CDS `brandai-platform-devupdate1012` 现有预览服务
范围：已知工作区、2026-10-19、用户反馈的 `竖版.jpg`，随后按同一文件摘要限定查询。未修改线上数据、服务或模型配置。

## 1. 已确认的事实

找到同一项目的三次上传记录，文件名与本轮反馈一致，三次文件内容摘要相同，均很快进入 `FAILED`。三次都记录了如下错误：

> 图片损坏或格式不受支持。请上传 4000 万像素以内的静态 PNG、JPEG 或 WebP。

| 尝试时间（北京时间） | 进入失败的耗时 | 状态 | 数据库错误分类 | 宽 / 高 | 生成素材 |
| --- | ---: | --- | --- | --- | --- |
| 10-19 12:33:48 | 1.799 秒 | FAILED | `UPLOAD_IMAGE_INVALID` | null / null | 无 |
| 10-19 12:35:26 | 1.468 秒 | FAILED | `UPLOAD_IMAGE_INVALID` | null / null | 无 |
| 10-19 13:05:18 | 2.225 秒 | FAILED | `UPLOAD_IMAGE_INVALID` | null / null | 无 |

三次声明 MIME 均为 `image/jpeg`，文件大小均为 **8,197,447 字节**，约 **7.82 MiB**，小于入口 10 MiB 限制。文件名和 MIME 都是上传声明，不能单独证明文件内部一定是 JPEG。字节数低于入口上限也不能证明像素数低于 4000 万。

这些记录与“同一个文件重新上传仍失败”的现象一致。截图未带任务身份，因此不把截图强行绑定到三次中的某一次；三次结果本身已经由真实数据库确认。

## 2. 初次失败发生在哪里

代码链路：

1. `apps/web/src/lib/studio-materials-policy.ts`：入口校验 multipart、声明 MIME、文件字节上限，建立上传任务。
2. `apps/web/src/lib/workers/studio-materials.worker.ts`：检查授权、内容摘要，然后调用图片验证。
3. `apps/web/src/lib/studio-materials-image.ts`：核对实际图片格式与声明 MIME、是否多帧、尺寸及像素上限，并用 Sharp `stats()` 强制完整解码。
4. 验证通过后才进入对象存储上传及 Asset 创建；验证抛出 `ApiException(422)` 时任务立即终止，并清空暂存图片字节。

三条任务都返回图片验证函数统一的错误文案，且没有生成 Asset。由现有实现和真实记录可以定位到**图片验证未通过**，没有证据表明是排队 6 分钟超时、调用 AI 失败或存储成功后丢了画布状态。

## 3. 不能继续下结论的部分

旧版本图片验证把以下情况都归为同一句 `UPLOAD_IMAGE_INVALID`：

- 声明 JPEG，但实际为其他格式；
- 图片格式不受支持；
- 多帧图片；
- 宽高超过单边限制，或超过 4000 万像素；
- 图片内容截断、损坏或 Sharp 完整解码失败。

**本次尚不能判定三次失败具体属于哪一种，也不能因此认定图片肯定损坏。**

13:18 左右的只读复查确认：

- 三条上传记录的暂存 `body` 都已清空；
- 三条记录都已标记对象清理完成；
- 同一工作区、同一文件摘要只有这三条失败，没有可复核的成功上传副本；
- 读取到的近期 worker 日志共 500 行，没有相关上传诊断前缀，未取得更细的错误类别。只保存了过滤结果，没有保存或输出整段日志。

因此当前数据库的 `width`、`height` 为 null，不能从本次材料推算原文件分辨率或 EXIF 方向。用户随后说明原文件是他人发来、暂不清楚保存位置，本轮不继续搜索无关私人文件。

## 4. 与首页“删不了、继续项目卡住”的关系

需要分开处理两个问题：

| 问题 | 本次证据能说明什么 | 处理方向 |
| --- | --- | --- |
| 原文件为何被拒绝 | 真实后端图片验证失败；细分类别尚不明 | 为后续上传提供明确的格式 / 多帧 / 像素 / 解码错误分类，保留安全校验 |
| 失败后删除按钮灰色，继续项目卡在图片交接 | 是失败终态的前端恢复问题，不能从数据库错误直接推出具体 UI 逻辑 | 主线程及并行智能体修复终态解锁、删除 / 重新选择、项目恢复流程，并做浏览器回归 |

修复前端恢复应允许用户放弃失败附件、换图或继续合适的创作流程，但不能把 `FAILED` 当成上传成功，更不能自动重复发起付费生成。

主线程计划将本地图片验证错误细分，并补充测试及安全诊断映射。这能改善**今后的**定位和提示，**不能反推出历史三次失败的具体子类**，也不代表此次原图片已经成功上传。

## 6. 前端恢复修复与独立回归补充

本地已复现并修复“后端已失败，首页却仍显示处理中、附件无法删除、交接阻塞项目”的独立前端问题。修前真实 Chrome 回执记录卡片 `queued`、删除与空白按钮禁用，原 File 实际仍在 IndexedDB；新增用例先出现 `queued !== error` 的红断言，原有 7 项首页用例仍通过，说明此前存在覆盖缺口。

修后允许移除已核实失败的附件、换图，或明确结束交接并进入保留的项目；未知上传或未知首次创作仍只能核对原请求。结束交接保留原文件为未提交草稿，不删除服务端项目或素材，不自动发起生成。刷新先核实任务；写入恢复记录失败会回滚，不提前清原图。

独立验证结果：协议 34 项、首页模块 Chrome 14 项、完整 Studio 壳 Chrome 5 项通过。完整壳真实点击了失败后结束、打开其他项目与刷新、保留需求和原图、新建空白项目、新文字首次创作仅一次。修前红回执、修后绿回执和代码复核边界见 [首页上传失败恢复验收](./home-upload-recovery-verification-2026-10-19.md)。

以上是本地恢复能力验证，没有重新上传用户原文件，也没有真实模型调用。历史三条 `UPLOAD_IMAGE_INVALID` 的具体内部原因仍缺原始字节和细分日志；不能因前端现在可退出交接就宣布该图片已成功上传。
