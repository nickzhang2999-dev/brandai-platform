# DF-2 Sol · Agent 编排研发蓝图

研发评审稿 · 2026-11-19 · 源码基线为当日核对的远端 main，提交 c2a719658bfc3cf9493978a8928f65b3240ea766。

## 先交付什么

设计师从画布发出一张品牌主视觉任务，切走页面，稍后从另一台设备进入同一项目，能找到原任务、已生成的图，以及还需要自己决定的事项。这是 2.0 的第一条端到端验收路径。品牌、权限、付费次数、审批记录都能沿该任务查到。先在现有 Web、worker、AI 服务及数据库中完成，不新增六套服务。

## 五个独立 P0 工单

以下是已核对的代码路径。线上各路径的发生率、模型耗时占比和已损失的图片数均待测。P0 表示列入本轮发布门槛，实施有先后。

| 工单与负责人角色 | 实施边界 | 验收用例 |
|---|---|---|
| 01 迟到结果归档 · 执行与存储 | 生成服务收到返回时，按工作区、任务、尝试、尺寸保存图片和回执，再尝试关联画布。保存走独立的有界步骤。超时后到达的可用图进入原任务的待采用区。取消、项目删除和权限撤销分别处理，遵循保留与删除策略。 | 用可控提供方延迟返回一张图，超过执行期限。确认只提交一次，图片可从原任务查看并采用；重复回执只有一个版本；后来编辑的画布不会被迟到图覆盖。 |
| 02 排队和执行分开计时 · 队列 | 记录入队、领取、实际向提供方发出请求和收到结果的时间。设排队截止、执行预算和结果保留期。当前领取阶段就会写 providerStartedAt，测上游耗时需独立记录发送时间。 | 模拟排队超过旧的六分钟、仍在新排队预算内，领取后获得完整执行预算。排队已超新期限的任务清楚标记“排队超时”，上游提交数为零。 |
| 03 中断恢复与对账 · 执行与数据 | 保留首个终态写入保护；将本地等待结束、上游付费尝试、结果保存分别记录。按持久任务号恢复，优先查已存结果及可查询的上游任务。上游仅支持同步响应且没有查询凭据时显示“结果未知”，再次付费需用户明确发起。 | 在发送前、发送后回执前、图片已存但数据库未关联、关联完成但浏览器未收到四处模拟中断，重启后逐项核对任务、资产和上游调用数；重复事件与过期 worker 均不能覆盖新版本。 |
| 04 多尺寸按目标执行 · 执行与队列 | 现有循环已支持部分成功。新增每个尺寸的稳定标识、结果、错误及配额预留，先以并发 1 验证，再按提供方与工作区限额启用 2。依赖主视觉确认的尺寸在审批后派生。 | 三个独立尺寸中一个失败，另两个能单独查看；手动补做只涉及失败尺寸；两个用户同时生成时总在途数不超限；对比相同输入的整批耗时、限流率和成本。 |
| 05 预检失败可处理 · 品牌与前端 | 将规则标识、来源版本、可编辑字段和下一步操作随错误返回。设计师可改文案或参考素材，有权限的维护者可修正规则。保留原草稿和硬性阻断。 | 用一条禁用表述触发拦截，定位原文，改正后复检并提交；未解决前上游生图调用为零；无规则管理权限者仍可修改自己的草稿。 |

**共用设计判断。** 如果网络断开时图片只存在于上游，且上游既不提供任务号也不保留可取回结果，数据库无法恢复那张图。01 的承诺限定为“结果已到我方可持久化边界，或上游有可核验结果”；03 负责向用户解释其余情况。只读查询可以重试，付费提交的重试必须知道前一次是否已受理。回调重复、对象存储写成但数据库写失败，由同一尝试号对账。

## 六个模块怎样接在一起

| 模块 | 保留、重构或新增 | 输入、输出与决定权 |
|---|---|---|
| Brand Intelligence 品牌知识 | 保留品牌知识、规则快照及 Zod/Pydantic 双契约 | Brief 与授权品牌资料形成带版本的约束包。计划、生成和质检引用同一快照。来源权限撤回时重新校验。 |
| Agent Orchestrator 任务编排 | 新增有边界的 Plan/Step，复用现有生成入口 | 将需求拆成可展示的步骤，标出依赖、预算和审批点。服务端校验工具、权限与预算后才能入队；编辑已批准步骤时重新校验受影响的后续步骤。 |
| Generator Registry 生成器目录 | 重构模型适配方式 | 每项声明能力、输入输出契约版本、尺寸限制、费用策略、能否查询历史结果。优先把一个现有生成器登记迁入。兼容协议可加配置，新协议需适配器及契约测试。 |
| Production Engine 生产执行 | 保留数据库任务记录、队列与现有 worker，重构恢复和结果归档 | 接收已批准步骤，记录尝试、调用和产物。按同一任务号向画布返回进度及结果，刷新、切后台和换设备均能查回。 |
| Visual QA 视觉质检 | 复用合规检查，补交付检查及证据 | 对照原图、规则快照和交付规格，分别标注商品颜色、Logo、文案与尺寸的检查结论。证据不足时交给设计师确认，保留可查看的原图与对应版本。 |
| Design Memory 设计记忆 | 新增候选提炼、确认、作用域与撤回 | 从版本和审核决定提炼经验，关联证据、适用项目、确认人和版本。设计师确认后用于本项目；跨项目需授权，升级品牌硬规则需品牌管理权限。撤回同步使检索缓存失效。 |

以“为绿苹果饮料做三种渠道尺寸”为例：工作单固定商品色和包装 Logo，设计师在预览选定构图；引擎记录主视觉及三个尺寸的依赖；画布中立即出现与任务号绑定的占位，重新进入项目时从服务端重建。质检发现某版本把绿苹果画成红色，只标出该版本和证据；其他合格版本可继续。设计师对该稿的修改理由可成为项目记忆候选，未经确认的偏好不会改写品牌规则。

## 实施顺序与发布决策

1. **建立基线。** 沿同一任务号记录排队、上游执行、存图、画布可见四段耗时；按提供方、尺寸数和并发数看 P50/P95，记录已收费尝试数、结果未知数、迟到可恢复数。当前没有实测数值，先用受控提供方复现，再以少量获准的真实任务校准。
2. **先做 01、03，再切 02。** 用新增可空字段与独立结果记录兼容在途旧任务；先记录与对账，再让新任务启用新期限。灰度回退可关闭新提交策略，保留旧任务读取、回执归档与对账。05 可并行做。
3. **完成 04，再交付持久画布占位。** 并发按工作区逐步放开，出现重复付费或结果覆盖即停止扩量。用两个并发任务、两个浏览器会话，分别验证切后台、刷新、换设备和局部失败。单张图的上游耗时单独报告。
4. **再上线第一条 Agent 工作流。** 限一个品牌、一个已有生成器、一种工作单，从 Brief、预览、按策略审批、生成、质检、最终审核走到交付和记忆候选。验收要求能说明每张图用的品牌版本、发生的实际调用、审批决定及可用范围。

**本期暂缓**：开放插件市场、自动选择任意模型、未知结果自动换供应商重生成、未经授权的跨品牌记忆、独立部署六个服务。本轮架构不依赖新模型采购。

## 扩展研究如何改变研发决策（11 月 19 日补订）

第一轮围绕四份主材料展开。扩展盘点后，五个 P0 的先后顺序仍成立。新增的实现要求按下面的验收场景并入对应工单或后续试点。表内“验收”均是 DeepFlare 拟做的测试。

| 落点 | 原始材料提供的线索 | DeepFlare 的具体决策与验收 |
|---|---|---|
| P0-02、03 与画布 | 动态调试报告记录了工具预计耗时字段。展示预估时间和判定任务死亡需要两套依据。动态调试（研究归档 `lovart/DYNAMIC_DEBUG_REPORT.md`） | 画布显示当前阶段、最近确认时间。积累本产品分阶段耗时样本后再显示预计等待区间。模拟超过预计时间而提供方仍在执行，卡片继续跟踪原任务，付费提交数保持一次。 |
| P0-05 与工作单 | 原始 feed 有 20 个条目，包含问题、输入模板和显示规则；执行样本记录了每个 Skill 可用的工具。卡片数据（研究归档 `lovart/all_skills_feed.json`） · 内容报告（研究归档 `lovart/SKILL_CONTENT_REPORT.md`） · 执行报告（研究归档 `lovart/SKILL_EXEC_REPORT.md`） | 区分“品牌商品主图”工作流和“生成/编辑图片”执行工具。已选商品、品牌和渠道从项目带入，只追问会改变交付的缺项。预检返回后保留已填值。服务端按工作流版本验证可用工具，越权步骤在调用前被阻止。 |
| Brand Intelligence 与 Design Memory | 方法论与 Skill 拆解区分可用参考和弱风格证据，纯文字截图或孤立 Logo 不足以判断完整风格。方法论（研究归档 `lovart/METHODOLOGY.md`） · 样本拆解（研究归档 `lovart/SKILL_MD_ANALYSIS_NOTES.md`） · Recraft 分站（研究归档 `re/reports/05-recraft.md`） | 在工作单分别记录商品原图、品牌硬规则和风格参考。用“黑白 Logo＋绿色商品原图”验收，Logo 单图不得派生全品牌黑白规则；参考冲突时展示依据，由有权限的人确认是否形成记忆。 |
