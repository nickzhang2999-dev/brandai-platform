# DF-2 Sol 首张主视觉的原生派发

2026-11-20，开发分支 `df-2-sol`。本批已完成本地实现和数据库验收。产品端出图与计费留待隔离试点验证。

## 工作单如何进入 Studio

1. 编辑者提交需求并确认具体方向。服务端将确认人、计划版本、画布与素材用途版本、执行键随派发记录保存。
2. 后台每 15 秒检查一次试点工作区，只领取已获准的新记录。首批只接第一张主视觉，按画布可生成的精确尺寸映射。缺少已批准模板的直接制作、尚未解析的灵感引用、无法匹配的尺寸会留下原因。
3. 派发时重新核对编辑权限和项目状态，再经过普通 Studio 的品牌规则、素材检查、容量限制与品牌所有者额度逻辑。额度预留、生成请求和工作单关联一起提交。事务失败时三者一起回滚。
4. 已受理请求交给既有 Studio 后台按原请求号投递。试点最多同时受理一个待生成或生成中的 Sol 请求。单次容量不足会延期；终止性失败保留原因。只有发起人可通过工作单回执取得原生请求号。

## 已验证

| 场景 | 实际结果 |
| --- | --- |
| 独立 PostgreSQL | 完整迁移在新数据库执行，再运行无待执行迁移；13 项集成测试通过。 |
| 普通 Studio 与 Sol 同时提交 | 各自获得不同的请求号，普通发起人可查询自己的任务；两个后台同时领取同一 Sol 工作单，最终只有一条原生请求。 |
| 在保存关联处注入数据库错误 | 生成请求与计入额度的生成记录全部回滚。解除故障、重新连接后，恢复使用同一执行键。投递替身收到原生请求号。 |
| 权限和容量 | 执行前被降为只读的成员触发拦截；缺模板依据的直接制作、非标准尺寸均未占用额度。第二个 Sol 请求在首个仍执行时保留排队。 |
| 兼容与暂停 | 历史审批不会随开关开启而补跑。HTTP 暂停时拒绝新写入，授权用户仍可查询历史。 |
| 代码回归 | Contracts 435、UI 42、Web 2707 项通过，Web 另有 95 项跳过。Python 940 项通过。Web 类型检查、生产构建和两项发布脚本检查通过。 |

## 运行设置与验收余项

Web 和 Worker 应使用同一组配置。在已隔离的试点，工作单 API 由 `DEEPFLARE_V2_ENABLED` 和明确的 `DEEPFLARE_V2_WORKSPACE_IDS` 控制。`DEEPFLARE_V2_NATIVE_DISPATCH` 默认为 `0`；`1` 开启新审批的受理；`paused` 保留授权历史读取并阻止新的工作单写入与派发。已经交给 Studio 的请求继续由原生机制跟踪。开关变更随进程配置生效。

验收数据库只监听本机。故障注入发生在数据库事务内；测试中服务就绪检查和 Redis 投递使用替身，没有调用付费模型。下一次在确认数据库、队列和对象存储隔离并登记预算后，同时提交一条普通画布任务和一条已确认方向的 Sol 工作单，逐条核对实际图片、画布取回、归属和账单。排队及执行分段计时、上游回执未知和迟到图片归档属于 PR-02。
