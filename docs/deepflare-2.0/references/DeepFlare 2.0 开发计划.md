## D0 开工基线与验收样本

1. **选定集成基线。** 本地 `claude/layer-quality` 有较新的灵感界面、共享库和主体保真实现，`claude/image26-migration` 有独立的图像模型升级提交。以目标部署需要的能力选定一个基线和提交，核对当前品牌、灵感数据、工作台和 Worker 在该版本能否跑通。将所需分支差异列成清单。 [灵感库开放范围记录](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/docs/worklog/2026-11-04-inspiration-opening.md)
2. **准备一次真实创作。** 选一个品牌、一个项目、一个真实 brief 和一个用途明确的灵感案例。挑可肉眼判断的借鉴点，例如「侧光加右侧留白」。保留当前手动找灵感、转述到工作台的操作和结果，作为接入前基线。
3. **准备搜索与边界用例。** 收集设计师实际会用的任务描述和检索词，覆盖关键词、分类筛选、宽泛描述、无结果、追问和带引用答案。另准备案例版本更新、撤回、权限变化和品牌切换的回归数据。

## D2 把灵感接进当前项目

### 用户流程

1. 在 Studio 输入区点「添加灵感」，或在 Ommi 案例详情点「用到当前项目」。当前项目自动带入，设计师确认借鉴点，可补本次用法。
2. 工作台显示已选参考，可查看出处、修改用法、移除或取消本轮使用。沿用现有收藏入口，明确选用才把做法接进创作。
3. 从常规 Studio 出图入口提交。结果的「本轮依据」显示实际送入生成的借鉴点和来源版本。设计师在审核时确认成品是否体现该方法。引用失效时，就地更换或移除。

### 数据和接口

| 对象 | 计划 |
|---|---|
| 现有收藏 | `InspirationBookmark` 保持个人所有权和原有用途。已有收藏可通过明确的「用到项目」动作转为项目引用。 |
| 项目灵感引用 | 首选扩展现有 `StudioProjectContext` 的可选引用字段，沿用项目范围、`expectedRevision` 和 mutation 回执。条目记录灵感库、案例及版本、选定要点、用法和创建人。相同版本和内容的重复选用复用已有记录。旧项目读为空集。 |
| 生成请求与结果 | 请求携带本轮选中的引用 ID。受理时冻结这些条目的版本与内容，沿用项目资料的快照方式。保存到项目的其他参考不随本轮发送。沿现有生成记录区分「本轮已选」「已送入生成」和「成品已核验」。 |
| 项目级接口 | 优先扩展现有项目资料接口及权限校验。写操作要求品牌编辑权限及项目归属，读操作同时校验当前成员和来源权限。先确认现有版本与快照能承接试点，再决定是否需要独立存储。 |

工作台保存的是可追溯的项目引用。首批发送经确认的文字借鉴点与必要约束。原图、全文和对话历史留在各自来源。现有案例卡片的 `analysisAllowed` 校验的是外部分析用途。D0 明确试点文字借鉴点的生成用途，接入时复用灵感库及案例版本校验。用途不明确的案例保留浏览入口并提示限制。代码核对点为 `77d565c`。 [项目资料冻结](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/apps/web/src/lib/studio-project-context.ts#L111) · [案例权限](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/apps/web/src/lib/inspiration/access.ts#L26)

### 生成链路

- **受理时。** 从现有 Studio 入口接收选中引用。用 `workspaceId`、`projectId` 和当前用户校验引用归属、有效版本及用途权限。把解析后的版本与作用范围绑定到现有生成请求和上下文摘要。相同提交沿用现有幂等与配额控制。
- **执行前。** Worker 在付费调用前再校验来源版本和权限。待执行引用若失效，标记本次请求待重新选择，避免把旧内容送给模型。发送借鉴点时与系统规则、用户原始 brief 分开，已确认品牌硬规则优先。
- **返回后。** 按现有品牌规则回执的做法，从 Worker 写入的证据投影结果，关联稿件版本及实际发送的借鉴点。当前选用的变化不改写旧结果。来源撤回后按现行权限控制历史详情。成品是否体现做法由审稿或现有可确定的检查另行确认。 [品牌规则回执实现](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/apps/web/src/lib/studio-brand-rule-receipt.ts#L30)

接入点先核对正常工作台提交经过的路径。直接提交和对话 Worker 最终都能走 `submitStudioGeneration`，验收必须覆盖试点用户实际使用的入口。若改动跨 TypeScript 与 Python 边界，同时更新相应契约和镜像测试。 [生成请求受理](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/apps/web/src/lib/studio-generation.ts) · [生成 Worker](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/apps/web/src/lib/workers/generate.worker.ts)

## D3 验收与发布

| 验收项 | 必须看到的结果 |
|---|---|
| 正常路径 | 当前项目 → 灵感搜索与选用 → 工作台实际出图 → 成品体现借鉴点 → 从结果回到案例。保留本次真实请求、产物和设计师审核证据。 |
| 选用与持久化 | 收藏、项目引用与本次勾选各自独立。刷新可恢复，重复添加不重复，移除后新任务不再读取。项目和品牌切换后的列表正确。 |
| 权限与版本 | 只读用户无法写入。跨品牌、跨项目、撤回、更新后的旧版本和未授权用途无法进入生成。排队后变更权限同样拦截。 |
| 异常与费用 | 来源不可用时提示修正。双击提交、重试和刷新不重复发起付费调用。生成失败时保留可理解的状态和可继续操作。 |
| 旧功能回归 | 未选灵感的常规生成、既有素材引用、收藏、问答和品牌切换仍能走原流程。浏览器实际走过页面，单独以真实服务验证生成质量。 |

## P1 当前项目的自动工作流

1. **P1.1 工作单与分派。** 借鉴 Lovart Skills 和 FLORA Techniques，先定义一个「品牌上新」工作单，声明商品原图、卖点、渠道、交付物与制作方式。用现有 TS Worker、任务 ID 和回执执行，保存状态和结果引用。 [Lovart Skills](https://www.lovart.ai/docs/how-to-prompt/agent-skills) · [FLORA 工具契约](https://docs.flora.ai/mcp/tools.md)
2. **P1.2 灵感岗位接入。** 按当前项目和来源权限检索 Ommi，用 P0 的引用契约输出带出处的方向。区分设计师选用与系统建议。缺必需参考时暂停对应步骤，补齐后从该步骤继续。
3. **P1.3 可选的方向确认。** 沿用 Studio 画布和右侧任务区，先用原图、占位和构图说明展示一版方向稿。精细模式保存方向版本及等待状态，期间只更新粗构图。确认时校验当前版本并复用现有幂等机制，同一确认只启动一次正式制作。批量直出沿工作单和模板继续执行。
4. **P1.4 正式制作与审阅。** 视觉岗位沿用同一条 Studio 生成链路。现有画布和原生文案承担版式组装，关键尺寸、Logo、商品标签等能确定的项直接校验。按原图图层或蒙版实际保护的范围报告保真，模型检查无法确认的交审核。评审绑定对应稿件版本，局部修改只重跑相关步骤。 [原生文案工作流](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/docs/canvas-copywriting.md) · [主体保真能力边界](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/docs/visual-fidelity-integration.md) · [现有版本审批接口](<https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/apps/web/src/app/api/workspaces/[wsId]/generations/[genId]/versions/[versionId]/review/route.ts>)
5. **P1.5 同项目审核写回。** 在审核区从有明确反馈的版本提炼候选。经设计师确认后保存经验及来源版本，默认当前项目。后一轮按适用条件读取，沿 P0 的结果回执回查。确认与撤回复用现有角色校验，撤回后新任务不再读取。

P1 验收分别跑精细模式和批量直出。核对草图修改与正式任务隔离、刷新和 Worker 重启后恢复等待、旧版本确认拦截、重复确认只执行一次。验证批量提交能直接进入制作，遇到缺料、规则冲突或付费结果不明时保留明确状态。沿用现有生成受理、队列恢复和付费幂等。 [现有会话 Worker](https://github.com/nickzhang2999-dev/brandai-platform/blob/77d565c93896/apps/web/src/lib/workers/studio-conversation.worker.ts#L90)

## P2 跨项目设计记忆

1. **扩大授权。** 从 P1 已确认且来源可追溯的项目经验中选少量案例，经授权扩大到同品牌同类任务。品牌长期规则继续走现有确认流程。
2. **筛选与读取。** 后续项目按品牌、项目权限、任务条件和来源有效性筛选，再把少量候选传给需要它的步骤。撤回与纠错影响后续读取，已完成稿件继续按当前权限展示回执。
3. **验证真实收益。** 在相同模型、预算、品牌规则和工作流下，对比开关历史案例，记录首轮通过率、人工改稿时间和同类错误复发。连续出现有证据的模型瓶颈后，再另行评估模型优化。

## 第一批可开工的任务

产品和设计先整理真实查询、目标案例及一个现有项目的验收记录。工程并行锁定基线，列出 D1 走查结果、D2 项目引用契约和 Studio 首个接入点。两边合起来产出一张首期验收单，依照 D1、D2、D3 的条件逐项交付。
